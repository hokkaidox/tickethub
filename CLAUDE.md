# TicketHub

Пет-проект для изучения распределённых систем: платформа продажи билетов на мероприятия. Java 25, Spring Boot 4, Kafka, PostgreSQL, Redis. Всё запускается локально через Docker Compose.

## Документация

- `docs/plan.md` — roadmap с чек-листами по этапам: один этап — один сервис.
- `docs/architecture.md` — диаграмма контейнеров, правила взаимодействия, sequence-диаграммы.
- `docs/adr/` — архитектурные решения в формате `docs/adr/template.md`.
- `docs/libs.md` — общие модули (стартеры, convention plugins, тестовые библиотеки) и правила их появления.

## Правила работы с документацией

- Если изменение затрагивает взаимодействие сервисов, топики Kafka, хранилища или контракты API, обнови `docs/architecture.md` в том же изменении.
- Значимое архитектурное решение фиксируй новым ADR со следующим номером. Принятый ADR не переписывай: если решение меняется, создай новый ADR со статусом «заменяет ADR-NNN», а у старого поменяй статус на «заменено ADR-NNN».
- Когда задача из `docs/plan.md` выполнена, отметь её чек-бокс.
- Диаграммы только на Mermaid, чтобы они отображались в Obsidian и на GitHub.
- Ссылки между документами — обычные markdown-ссылки с относительными путями, не wiki-ссылки.

## Архитектурные принципы

- У каждого сервиса своя БД; чужую БД напрямую не читать.
- Синхронный вызов — только там, где пользователь ждёт ответа. Остальное — события через Kafka.
- Через transactional outbox публикуется событие, потеря которого оставит сервисы в разошедшемся состоянии (итог платежа, истечение брони, подтверждение заказа). Событие с самовосстановлением, например инвалидацию кэша, которую подстрахует TTL, можно отправлять после коммита без outbox.
- Любой вызов, который может повториться, идемпотентен: ключ идемпотентности для REST, inbox для потребителей Kafka.

## Контракты между сервисами

- Контракт — это файл, а не Java-классы: `contracts/<сервис>/openapi.yaml` для REST и `contracts/<сервис>/events/*.avsc` для событий. Владелец контракта — сервис, именем которого названа папка.
- Владелец работает API-first: интерфейсы контроллеров и модели генерируются из `openapi.yaml` в `build/` и не коммитятся. Контроллер реализует сгенерированный интерфейс.
- Общих jar с DTO или готовыми клиентами нет. Потребитель пишет свой клиент (`@HttpExchange`) и свои DTO в `adapter/out/http/<сервис>/`: только нужные ему эндпоинты и поля. Таймауты, retry и circuit breaker задаёт потребитель.
- DTO не выходят за пределы адаптера: контроллер переводит запрос в команду use case, клиент переводит ответ в тип порта.
- Совместимость проверяется в CI: oasdiff для OpenAPI, проверка совместимости Avro для событий, Pact между потребителем и владельцем. Ломающее изменение делается только через новую версию (`/v2`, новая версия схемы).
