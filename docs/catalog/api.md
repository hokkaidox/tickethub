# API Catalog (набросок)

Набросок REST API Catalog, по которому пишется `contracts/catalog/openapi.yaml`. Контракт — источник истины; когда он появится, этот файл описывает только решения, которых в контракте не видно. Модель данных — в [ERD Catalog](erd.md), группы эндпоинтов — в [ADR-020](../adr/0020-endpoint-groups.md).

## Контроллеры и теги

Контроллер — на ресурс и группу, а не на таблицу. Схема зала, её сегменты и места — один неизменяемый агрегат, поэтому у `segment` и `seat` своих контроллеров нет. Цены мероприятия принадлежат контроллерам мероприятия.

Каждый контроллер реализует ровно один интерфейс, сгенерированный по тегу:

| Пакет | Контроллер | Тег → интерфейс |
| --- | --- | --- |
| `web/api` | `VenueController` | `venues` → `VenuesApi` |
| | `LayoutController` | `layouts` → `LayoutsApi` |
| | `EventController` | `events` → `EventsApi` |
| `web/admin` | `AdminVenueController` | `admin-venues` → `AdminVenuesApi` |
| | `AdminLayoutController` | `admin-layouts` → `AdminLayoutsApi` |
| | `AdminEventController` | `admin-events` → `AdminEventsApi` |
| `web/internal` | `InternalEventController` | `internal-events` → `InternalEventsApi` |

Почему контроллеры поделены по группам:

- у групп разные гарантии чтения (кэш и только `PUBLISHED`, БД и все статусы, точные цены без кэша); в одном классе легко вызвать не тот метод сервиса, и ошибка будет незаметной;
- у групп свои DTO и маппинг;
- пакет на группу даёт границу, которую проверяет ArchUnit: контроллер из `web/admin` реализует только `Admin*Api` и т. д.

Layout отделён от Venue: у площадки тривиальный CRUD, а у схемы самая тяжёлая логика Catalog — проверка рядов, разворачивание мест, запрет удаления используемой схемы, публичное чтение с вечным кэшем.

## Сервисы

Сервисы делятся по ресурсу, а не по группе: группа — понятие транспорта, use case у групп один ([ADR-020](../adr/0020-endpoint-groups.md)).

| Сервис | Что делает |
| --- | --- |
| `VenueService` | Создание, изменение, чтение площадок |
| `LayoutService` | Создание схемы с разворачиванием мест, удаление неиспользуемой, чтение |
| `EventService` | Создание, цены, публикация и отмена (с outbox), чтение |

Разные гарантии чтения — разные методы одного сервиса. Метод называется по гарантии, а не по вызывающему:

```java
@Cacheable("events")
Event getPublished(UUID id);                                     // web/api: кэш, только PUBLISHED
Event get(UUID id);                                              // web/admin: из БД, все статусы
List<SeatPrice> pricesFor(UUID eventId, List<Integer> seatNos);  // web/internal: из БД
```

Если `EventService` разрастётся, он делится на чтение и запись (`EventQueryService`, `EventCommandService`), а не по группам, и только когда действительно разрастётся.

## Эндпоинты

Пути указаны без префикса версии: `/api/v1`, `/admin/v1`, `/internal/v1`.

| Контроллер | `/api` | `/admin` | `/internal` |
| --- | --- | --- | --- |
| `VenueController` | `GET /venues`, `GET /venues/{id}` — через кэш | `POST /venues`, `GET /venues`, `GET /venues/{id}`, `PATCH /venues/{id}` — чтение из БД | — |
| `LayoutController` | `GET /layouts/{id}` — схема, сегменты и места | `POST /venues/{venueId}/layouts`, `GET /venues/{venueId}/layouts`, `DELETE /layouts/{id}` | — |
| `EventController` | `GET /events` — афиша, `GET /events/{id}`, `GET /events/{id}/prices` — только `PUBLISHED`, через кэш | `POST /events`, `GET /events?status=…`, `GET /events/{id}`, `PATCH /events/{id}`, `PUT /events/{id}/prices`, `POST /events/{id}/publish`, `POST /events/{id}/cancel` — чтение из БД, все статусы | `GET /events/{id}/prices?seatNo=…` — из БД, без кэша, scope `catalog:prices` |

Списки (`GET /venues`, `GET /events`, `GET /venues/{venueId}/layouts`) отдаются с курсорной пагинацией: параметры `Cursor` и `Limit` из `contracts/common/pagination.yaml`, у каждого списка своя схема страницы (`VenuePage`, `EventPage`, `LayoutPage`) вида `{ "items": [...], "nextCursor": "…" }`. Курсор непрозрачный, внутри ключ сортировки:

| Список | Сортировка и ключ курсора |
| --- | --- |
| Афиша `GET /api/v1/events` | По дате начала: `(starts_at, id)` |
| Мероприятия в админке `GET /admin/v1/events` | По дате начала: `(starts_at, id)` |
| Площадки, схемы залов | По времени создания: `id` (UUIDv7) |

## Чтение в админке и публичное чтение

У изменяемых ресурсов (площадка, мероприятие) чтение в админке отдельное от публичного, хотя оба метода вызывают один use case:

- **Свои изменения видны сразу.** Публичное чтение идёт через L1 и L2 с TTL. Администратор после `PATCH` увидел бы старые данные; админка читает из БД.
- **Админка видит всё.** Публичная афиша отдаёт только `PUBLISHED`, черновики и отменённые мероприятия видны только в `/admin`.

У неизменяемой схемы зала чтения в админке нет: устаревать нечему, черновиков нет, хватает публичного `GET /layouts/{id}`.

## Создание схемы зала

Схема создаётся целиком одним запросом вместе с сегментами и местами:

```http
POST /admin/v1/venues/{venueId}/layouts
```

```json
{
  "name": "Big hall",
  "segments": [
    { "key": "PARTERRE", "name": "Parterre" },
    { "key": "BALCONY", "name": "Balcony" }
  ],
  "rows": [
    { "section": "A", "row": "1", "from": 1, "to": 30, "segment": "PARTERRE" },
    { "section": "A", "row": "2", "from": 1, "to": 30, "segment": "PARTERRE" },
    { "section": "B", "row": "1", "from": 1, "to": 25, "segment": "BALCONY" }
  ]
}
```

- `key` сегмента живёт только внутри запроса, чтобы ряды могли на него сослаться. UUID сегментам присваивает сервер.
- Сегмент обязателен: `segments` содержит хотя бы один сегмент, у каждого ряда есть `segment`. В зале без зон администратор передаёт один сегмент, например `{ "key": "GENERAL", "name": "General" }`. Сервер неявный сегмент не создаёт.
- `section` и `row` необязательны: в зале без секций или без рядов поле просто не передаётся. Пустая строка запрещена (`minLength: 1`), чтобы у «нет секции» было одно представление, и в ответе поле тоже отсутствует, а не равно `null`. Секции в одной схеме могут быть у одних рядов и отсутствовать у других.
- Места передаются диапазонами по рядам: стадион на 50 000 мест — около 2 000 рядов, а не 50 000 элементов.
- Сервер разворачивает диапазоны в строки `seat` и присваивает `seat_no` от 0 до N−1 в порядке рядов запроса.
- Ошибки — 422 `INVALID_LAYOUT`: ряд ссылается на несуществующий `key`, `key` повторяется, сегмент без рядов, `from > to`, одно место встречается дважды.

Изменения схемы нет, в том числе сегментов: ни переименования, ни замены. Почему — в [ERD](erd.md), раздел «Правила». Даже переименование сломало бы вечный кэш `GET /layouts/{id}`. Новые сегменты — новая схема. Удалить схему можно, только пока на неё не ссылается ни одно мероприятие, иначе 409 `LAYOUT_IN_USE`. Если пересоздавать схему вручную станет неудобно, позже можно добавить копирование: тот же `POST` с `sourceLayoutId`.

## Ответы со схемой зала

Две отдельные схемы ответа, без `allOf`:

| Схема | Где | Поля |
| --- | --- | --- |
| `Layout` | `GET /api/v1/layouts/{id}`, ответ на создание | `id`, `venueId`, `name`, `seatCount`, `segments`, `seats` |
| `LayoutSummary` | элемент `LayoutPage` в `GET /admin/v1/venues/{venueId}/layouts` | `id`, `name`, `seatCount` |

- `seatCount` хранится в `layout.seat_count` и не меняется, отдавать его бесплатно. В `Layout` он избавляет клиента от подсчёта мест, в `LayoutSummary` показывает вместимость, когда администратор выбирает схему для мероприятия, а тащить в список десятки тысяч мест каждой схемы нельзя. Имя то же, что в `EventPublished`.
- `GET /api/v1/layouts/{id}` отдаёт схему целиком. Ответ никогда не меняется, поэтому кэшируется без TTL.
- На стадион в 50 000 мест массив `seats` весит 3–4 МБ JSON. Кэш выручает только сервер, клиент скачивает ответ целиком, поэтому ответы клиенту сжимает gzip на Gateway: повторяющиеся имена полей и UUID сегментов сжимаются в разы. Сам Catalog не сжимает: внутри Docker-сети это лишняя работа CPU. До этапа 8 Gateway нет, и ответ идёт несжатым; локально это не мешает. Если gzip не хватит, следующий шаг — отдавать места рядами-диапазонами, как в запросе на создание, но это новая версия ответа.

## Площадка: часовой пояс и валюта

- `timeZone` (IANA, `Asia/Almaty`) и `currency` (ISO 4217) обязательны при создании площадки. Неизвестный пояс или код валюты — 400.
- Время мероприятия хранится моментом (`timestamptz`), а отдаётся со смещением часового пояса площадки: `2026-12-01T19:00:00+05:00`. Клиент показывает «19:00» без пересчёта в свой пояс: начало концерта в Алматы не зависит от того, откуда смотрят афишу. В запросе принимается любое смещение.
- Валюта площадки — валюта её новых мероприятий. Смена валюты площадки на созданные мероприятия не влияет.

## Мероприятие

- `POST /admin/v1/events` создаёт мероприятие в статусе `DRAFT` на заданной схеме (`layoutId`). Площадка следует из схемы, валюта копируется с площадки. Несуществующая схема — 422 `LAYOUT_NOT_FOUND`: это ссылка в теле, а не ресурс в пути.
- `PATCH /admin/v1/events/{id}` зависит от статуса:

  | Статус | Что можно менять | Иначе |
  | --- | --- | --- |
  | `DRAFT` | Всё, включая `layoutId`. Смена схемы удаляет цены: они принадлежат сегментам старой схемы | — |
  | `PUBLISHED` | Только `description` | 409 `EVENT_FIELD_FROZEN` |
  | `CANCELLED` | Ничего | 409 `EVENT_CANCELLED` |

  Название, даты и схема после публикации заморожены: название и дата печатаются на проданных билетах, а места по схеме уже созданы в Reservation. Order копирует их в заказ при продаже, и после изменения купленные билеты разошлись бы с афишей. Описание на билет не попадает, поэтому опечатку в нём исправить можно. Перенос даты — отдельный сценарий с уведомлением покупателей, сейчас не моделируется.
- `PUT /admin/v1/events/{id}/prices` заменяет цены целиком: `{ "prices": [{ "segmentId", "amount" }] }`. Валюты в запросе нет: суммы в валюте мероприятия, и передать чужую валюту нельзя. Замена целиком идемпотентна сама по себе. Цены можно менять и после публикации: заказ хранит цену на момент создания.
  - 422 `INVALID_PRICES`: сегмент не из схемы мероприятия или повторяется; у опубликованного мероприятия нельзя убрать цену сегмента, иначе его места станет нельзя продать.
- Публикация и отмена — отдельные действия, а не `PATCH status`: у них есть проверки и побочные эффекты.
  - `POST …/publish`: только из `DRAFT` и только если у всех сегментов есть цены (иначе 422 `PRICES_INCOMPLETE`); пишет `EventPublished` в outbox. Повторный вызов на опубликованном мероприятии возвращает 200 без нового события. Публикация отменённого — 409 `EVENT_CANCELLED`.
  - `POST …/cancel`: у опубликованного мероприятия пишет `EventCancelled` в outbox ([ADR-012](../adr/0012-event-cancellation-orchestration.md)). Черновик отменяется без события: о нём никто не знает. Повторная отмена возвращает 200 без нового события.
- `GET /internal/v1/events/{id}/prices?seatNo=0&seatNo=1` возвращает точную цену по каждому месту (место → сегмент → цена) для фиксации в заказе, до 100 мест за запрос. Ошибки: 409 `EVENT_NOT_ON_SALE` для черновика и отменённого, 422 `SEAT_NOT_FOUND` для `seatNo` вне схемы.

### Ответы с мероприятием

| Схема | Где | Что внутри |
| --- | --- | --- |
| `Event` | `GET /api/v1/events/{id}` | Мероприятие без статуса (публично видны только опубликованные) и без цен |
| `EventSummary` | Элемент `EventPage` в афише | Плюс `venueName` и `minPrice`: карточке афиши нужны название площадки и «от 5 000 ₸», и без них клиент делал бы два лишних запроса на каждую карточку |
| `EventPrices` | `GET /api/v1/events/{id}/prices`, ответ на `PUT …/prices` | Цены по сегментам |
| `AdminEvent` | Чтение и изменение в админке | Всё, включая статус, валюту и цены: администратору нужны цены черновика, а публичный эндпоинт цен отдаёт только опубликованные |
| `AdminEventSummary` | Элемент `AdminEventPage` | Со статусом, без цен |
| `SeatPrices` | `/internal` | Цена по каждому запрошенному месту |

Цены отдаются отдельным эндпоинтом, а не внутри `Event`: на странице мероприятия клиенту нужны схема зала (кэш без TTL), мероприятие и цены, и меняются они с разной частотой. `EventPrices` и `SeatPrices` — не списки с пагинацией, а один ресурс «цены мероприятия»: их число ограничено числом сегментов (до 100) или запрошенных мест.

### Афиша

- Публичный список отдаёт только опубликованные мероприятия, по умолчанию будущие: `from` равен текущему моменту. Прошедшие уходят из афиши без смены статуса: статус «завершено» не нужен, он следует из даты. По id прошедшее мероприятие остаётся доступным.
- Фильтры: `venueId`, `from`, `to`; в админке ещё `status`, и `from` по умолчанию не задан.
- Курсор привязан к фильтрам: курсор, полученный с другими фильтрами, — 400 `INVALID_CURSOR`. Иначе продолжение страницы смешало бы две разные выборки.

## Деньги в JSON

Сумма передаётся объектом `{ "amount": "5000.00", "currency": "KZT" }`, сумма строкой с двумя знаками после точки. Число в JSON клиент на JavaScript прочитает как float и потеряет точность. Целое в минимальных единицах (тиынах) требует знать, сколько знаков у валюты, и неудобно при отладке. В запросе, где валюта известна из контекста, передаётся только `amount`.

## Ключ идемпотентности

Админские `POST`, которые создают ресурс (площадка, схема, мероприятие), принимают необязательный заголовок `Idempotency-Key` из `contracts/common/idempotency.yaml`. Остальные операции идемпотентны сами: `PATCH` и `PUT` задают итоговое состояние, повторные публикация и отмена возвращают 200 без побочных эффектов.

- Ключ генерирует программа, а не человек: админка создаёт UUID один раз на отправку формы и повторяет его при ретрае после таймаута.
- Без ключа запрос выполняется как обычно. Цена дубля в админке — лишний черновик, который администратор увидит и удалит, поэтому заголовок не обязателен. В Order, где дубль — второе списание денег, он обязателен.
- Сервер хранит ключ, хэш тела и ответ 24 часа в таблице `idempotency_key`. Повтор с тем же ключом получает сохранённый ответ; тот же ключ с другим телом — 422 `IDEMPOTENCY_KEY_REUSED`; повтор, пока первый запрос выполняется, — 409 `REQUEST_IN_PROGRESS`.
- Ключ уникален в паре с вызывающим (`sub` из JWT). До этапа 3 Keycloak нет, и ключ уникален глобально.
- Код живёт в Catalog и выносится в `idempotency-starter` на этапе 3, когда появится второй пользователь — Order ([libs.md](../libs.md)).
