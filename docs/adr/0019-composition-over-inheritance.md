# ADR-019. Композиция вместо наследования классов

- Статус: принято
- Дата: 2026-10-15

## Контекст

В Spring-проектах быстро появляются базовые классы ради переиспользования кода: `BaseEntity` с `id` и `version`, `AbstractService`, `AbstractIntegrationTest` с контейнерами. Каждый такой класс связывает наследников: изменение предка меняет поведение всех сразу, наследник получает поля и методы, которые ему не нужны, а прочитать класс можно только вместе с цепочкой предков. В монорепозитории с несколькими сервисами такой предок к тому же тянется в общий модуль, а правила [libs.md](../libs.md) запрещают там доменные типы.

Полностью без `extends` обойтись нельзя: исключения наследуют `RuntimeException`, а часть точек расширения Spring — абстрактные классы. В плане уже есть `AbstractRoutingDataSource` (шардирование, этап 6), `OncePerRequestFilter` (`idempotency-starter`), `ResponseEntityExceptionHandler` (ProblemDetail в `web-starter`).

## Решение

Мы не наследуем классы своего кода. Поведение переиспользуется композицией: внедрённым компонентом, делегатом или функцией.

Разрешено:

- **Реализация интерфейсов.** Контроллер реализует интерфейс, сгенерированный из OpenAPI; адаптер реализует порт.
- **Sealed-интерфейсы с records для закрытых наборов вариантов.** Состояния брони, заказа и платежа — `sealed interface` и `switch` с проверкой полноты при компиляции.
- **Иерархии исключений,** включая собственный базовый класс доменных ошибок сервиса.
- **Наследование абстрактных классов фреймворка** в адаптерах, конфигурации и стартерах. Наследник остаётся тонким, доменной логики в нём нет.

Запрещено наследовать класс из пакетов проекта, если это не исключение. В доменном слое (`domain` в hexagonal, модель в layered) классы не наследуют ничего, кроме `Object`, `Record`, `Enum` и исключений.

Общая настройка тестов тоже собирается композицией: мета-аннотация `@IntegrationTest` из `test-support` объединяет `@SpringBootTest` и импорт нужных конфигураций Testcontainers с `@ServiceConnection`. Базового класса для тестов нет.

Правила проверяет ArchUnit из `architecture-rules` для всех сервисов, независимо от layered или hexagonal.

## Рассмотренные варианты

- **Полный запрет `extends`.** Невыполним: исключения и точки расширения Spring требуют наследования. Обходить их пришлось бы обёртками, которые только запутывают код.
- **«Предпочитать композицию» как рекомендация без проверки.** Без ArchUnit-правила базовые классы появятся при первом же повторе трёх строк, и заметят их только на ревью.
- **Разрешить абстрактные базовые классы внутри одного сервиса.** Граница «внутри сервиса» не мешает `BaseEntity` и `AbstractIntegrationTest`, а именно они чаще всего превращаются в свалку общего кода.

## Последствия

- (+) Класс читается без цепочки предков; изменение одного компонента не меняет поведение посторонних классов.
- (+) Тест подключает только нужные контейнеры, а не все, что когда-то попали в базовый класс.
- (+) Состояния state machine проверяются компилятором через sealed-иерархии.
- (−) Пара одинаковых полей (`id`, `version`) повторяется в нескольких сущностях.
- (−) Наследование класса фреймворка вне адаптеров, например в слое use case, ArchUnit-правило не ловит: это остаётся на ревью. Если правило мешает законной точке расширения, его уточняют, а не обходят.
