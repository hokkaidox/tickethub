# ADR-013. Сервлетный стек без реактивного программирования

- Статус: принято
- Дата: 2026-09-29

## Контекст

Spring предлагает два стека: сервлетный (Spring MVC) и реактивный (WebFlux). Spring Cloud Gateway исторически реактивный, но у него есть вариант на MVC. Если Gateway будет реактивным, а сервисы сервлетными, общие стартеры (`security-starter`, `web-starter`) придётся писать в двух вариантах.

Нагрузка в TicketHub в основном I/O: БД, Redis, Kafka, HTTP-вызовы между сервисами. Java 25 даёт виртуальные потоки, которые решают ту же задачу масштабирования по I/O, что и реактивный стек, но с обычным блокирующим кодом.

## Решение

Все сервисы, включая Gateway, работают на сервлетном стеке: Spring MVC, `RestClient`, JDBC и виртуальные потоки. Gateway — Spring Cloud Gateway Server Web MVC. WebFlux, `WebClient` в реактивном режиме и R2DBC не используются.

## Рассмотренные варианты

- **WebFlux во всех сервисах.** Сложнее писать, отлаживать и читать трейсы, контекст (security, трейсинг) передаётся не через `ThreadLocal`. Для целей проекта выигрыша по сравнению с виртуальными потоками нет.
- **WebFlux только в Gateway.** Стандартный выбор для Spring Cloud Gateway, но это два стека в одном проекте и две версии общих стартеров.

## Последствия

- (+) Один стек и один набор стартеров для всех сервисов.
- (+) Обычный блокирующий код, понятные стек-трейсы, `ThreadLocal`-контекст работает.
- (+) Сравнение виртуальных и платформенных потоков в фазе 8 становится честным: это единственный способ масштабирования в проекте.
- (−) MVC-вариант Spring Cloud Gateway моложе реактивного, часть фильтров и примеров есть только для реактивного.
- (−) Виртуальные потоки не ограничивают число одновременных запросов сами: пулы соединений (HikariCP, HTTP-клиенты) и bulkhead становятся главными ограничителями, их нужно настраивать явно.
