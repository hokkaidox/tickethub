# ADR-020. Группы эндпоинтов: public, admin, internal

- Статус: принято
- Дата: 2026-10-19

## Контекст

REST-эндпоинты сервисов вызывают три разных вида клиентов: покупатели, администраторы и другие сервисы TicketHub (Order вызывает Catalog, Reservation и Payment). У них разная авторизация: роль пользователя или scope токена client credentials. Иногда и гарантии разные: клиенту цены для карты зала можно отдавать из кэша, а Order фиксирует цену в заказе и должен получить точную.

Если группы не разделены, правило доступа приходится ставить на каждый метод, и эндпоинт, на который его забыли поставить, оказывается открыт. Gateway при этом не может отличить внутренний эндпоинт от публичного и проксирует всё подряд.

## Решение

Эндпоинты делятся на группы по префиксу пути:

| Префикс | Кто вызывает | Через Gateway | Авторизация |
| --- | --- | --- | --- |
| `/api/v1/...` | Покупатель | Да | JWT пользователя, роль `customer`; чтение афиши — анонимно |
| `/admin/v1/...` | Администратор | Да | JWT пользователя, роль `admin` |
| `/internal/v1/...` | Сервисы TicketHub | Нет | JWT client credentials, scope вида `<сервис>:<действие>` |
| `/webhooks/...` | Внешний провайдер (только Payment) | Нет, провайдер вызывает Payment напрямую | HMAC-подпись |

1. **Gateway проксирует только `/api/**` и `/admin/**`.** `/internal/**` снаружи недоступен. Проверка токена в сервисе при этом остаётся: префикс — второй слой защиты, а не замена первого.
2. **Правила доступа задаются шаблонами путей** в `security-starter`, а не аннотациями на методах. Запрос, не попавший ни в одну группу, отклоняется. Конкретный scope внутреннего эндпоинта задаёт сервис.
3. **Если потребителям нужны разные гарантии, это разные эндпоинты.** Публичные цены Catalog отдаёт через кэш, внутренние для Order — из БД по конкретным местам. По той же причине у изменяемых ресурсов чтение в админке отдельное от публичного: администратор должен сразу видеть свои изменения (из БД, без кэша) и видеть то, что скрыто от публики (черновики, отменённые мероприятия). Неизменяемым ресурсам хватает публичного чтения. Оба метода вызывают один use case, различаются только адаптер и DTO.
4. **Один `openapi.yaml` на сервис, у каждой операции ровно один тег `<группа>-<ресурс>`:** `events`, `admin-events`, `internal-events`. У публичной группы префикса в теге нет. Генератор создаёт интерфейс на тег (`EventsApi`, `AdminEventsApi`, `InternalEventsApi`), и каждый контроллер реализует ровно один из них. Контроллеры лежат в пакете своей группы (`web/api`, `web/admin`, `web/internal`), а сервисы по группам не делятся: use case один, разные гарантии чтения — разные методы сервиса. Группу определяет путь, тег её только повторяет для генератора; соответствие «`/admin/**` ↔ `admin-*`, `/internal/**` ↔ `internal-*`, `/api/**` ↔ тег без префикса» проверяется в CI. Внутренний API — такой же контракт, с теми же проверками совместимости (oasdiff, Pact).

До этапа 8 Gateway нет, и клиенты обращаются к сервисам напрямую. На это время `/internal` защищён только токеном и scope.

## Рассмотренные варианты

- **Админка читает через публичные эндпоинты.** Меньше методов, но администратор после изменения видит устаревшие данные из кэша, а черновики мероприятий ему прочитать негде.
- **Без разделения, авторизация аннотациями на методах.** Забытая аннотация открывает эндпоинт; Gateway проксирует внутренние вызовы наружу.
- **Внутренние эндпоинты на отдельном порту.** Сильнее изолирует сеть, но удваивает настройку сервера, health-check и тестов. Для Docker Compose префикса и маршрутов Gateway достаточно; в Kubernetes (этап 10) изоляцию можно усилить NetworkPolicy.
- **Отдельный контракт на каждую группу.** Больше файлов и настроек генерации, а проверки совместимости одинаковы для всех групп. Теги дают то же разделение интерфейсов в одном файле.
- **Тег только по группе (`public`, `admin`, `internal`).** Генератор создал бы по одному интерфейсу на группу со всеми ресурсами сразу, и контроллеры по ресурсам стали бы невозможны.
- **Два тега на операцию: группа и ресурс.** Операция попала бы в два сгенерированных интерфейса, и контроллер получил бы один метод дважды. Двухуровневую навигацию в документации даёт расширение `x-tagGroups`, которое генератор игнорирует.

## Последствия

- (+) Новый эндпоинт под `/internal` или `/admin` защищён по умолчанию.
- (+) Gateway отсекает внутренние вызовы снаружи, даже если в сервисе ошиблись с проверкой scope.
- (+) Контроллеры небольшие: по одному на группу.
- (−) Один и тот же ресурс может появиться в двух группах (цены), и их нужно держать согласованными.
- (−) До этапа 8 вторым слоем защиты `/internal` ничего не служит.
