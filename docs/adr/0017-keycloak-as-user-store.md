# ADR-017. Keycloak как хранилище пользователей, без собственного сервиса пользователей

- Статус: принято
- Дата: 2026-09-30

## Контекст

Заказ, бронь и платёж оформляются на конкретного покупателя, а Order и Payment шардируются по user_id. Значит, у системы должны быть пользователи: регистрация, вход, email для писем.

В системе уже есть Keycloak: он выдаёт JWT пользователям и сервисам. Своего доменного поведения у пользователя в TicketHub нет: ни профиля покупателя, ни лояльности, ни настроек — только личность и контакт.

## Решение

Keycloak — единственный источник пользователей. Регистрация идёт через self-registration Keycloak с подтверждением email, вход — через Authorization Code + PKCE. Отдельного сервиса пользователей нет.

- userId — это `sub` из JWT пользователя. Сервисы хранят его как непрозрачный идентификатор и не держат копию профиля.
- Order при создании заказа берёт email из claim `email` токена и сохраняет его в заказе как снимок. Email передаётся в событиях заказа, поэтому Notification не обращается к Keycloak.
- Роли задаются в realm Keycloak: `customer` для покупателей, `admin` для управления каталогом и отмены мероприятий.

## Рассмотренные варианты

- **Собственный сервис пользователей.** Дублирует то, что Keycloak уже делает (хранение учётных данных, подтверждение email, сброс пароля), и добавляет ещё один синхронный вызов на пути покупки. Оправдан, когда у пользователя появляется своя доменная логика.
- **Гостевая покупка без аккаунтов.** Проще для покупателя, но ключ шардирования, rate limit по пользователю, доступ к своим заказам и история заказов пришлось бы строить на email, IP и секретных ссылках.
- **Notification читает email из Keycloak Admin API.** Всегда актуальный адрес, но это синхронная зависимость потребителя Kafka от Keycloak и лишний служебный доступ к данным пользователей.

## Последствия

- (+) Регистрация, вход, подтверждение email и сброс пароля готовы без кода.
- (+) user_id есть в каждом заказе с первого этапа, шардирование по нему (ADR-005) работает без изменений.
- (−) Email в заказе — снимок: если пользователь сменит адрес в Keycloak, письма по старым заказам уйдут на старый адрес.
- (−) Удаление пользователя в Keycloak не распространяется на данные в сервисах; если понадобится, это отдельная задача через события администратора Keycloak.
- (−) Решение стоит пересмотреть, если у пользователя появится своё поведение: профиль, предпочтения, лояльность. Тогда появляется сервис пользователей, а Keycloak остаётся только провайдером идентичности.
